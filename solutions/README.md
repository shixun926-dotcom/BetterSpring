## 1. 为什么要有这个目录

`campus/` 展示的是**最终态**，不是**逐关态**。

等你做到 Lv05，`campus/` 里已经混进了 Lv04、Lv05 的代码 ——
想回头看"Lv03 那关当时代码该长什么样"，已经做不到。

`solutions/` 补的就是这个缺口：**把每一关通关那一刻的工程状态冻结下来**。

| 目录 | 是什么 | 用途 |
| --- | --- | --- |
| `campus/` | **活的工程**，随关卡不断演进 | 开发、运行 |
| `solutions/LvNN/campus/` | **冻结的快照**，记录 LvNN 通关那一刻 | 对照、复习、卡住时解救 |

## 2. 目录约定

```
solutions/
├── README.md                    本文件
├── Lv01/
│   ├── README.md                本关做了什么 / 怎么验收 / 与上一关的差异
│   └── campus/                  ← 本关新增或改动的文件
│       └── ...（路径与仓库根的 campus/ 一一对应）
└── Lv02/ ... 后续关卡
```

📌 **映射规则**：`solutions/LvNN/campus/<路径>` ≡ 工程里的 `campus/<路径>`。
所以对照方式很简单 —— 打开同名路径直接比。

📌 **只放"本关增量"**，不放整份工程。想看/跑某一关的**完整可运行状态**，用 git tag：

```bash
git checkout lv01-pass      # 切到 Lv01 通关那一刻的完整工程
git checkout main           # 回到最新
```

| tag | 含义 |
| --- | --- |
| `lv01-pass` | Lv01 通关 |
| `lvNN-pass` | 后续关卡，逐关追加 |

## 3. 使用规则（硬约定）

📌 与 [`docs/00-文档使用与维护规范.md`](../docs/00-文档使用与维护规范.md) §10 一致。

| ID | 规则 |
| --- | --- |
| `SOL-001` | 参考解**只用于对照和卡住时的解救**，不得作为默认阅读顺序。学习时只打开当前关卡讲义 |
| `SOL-002` | **允许查看的门槛**：本关 §6 的"故意制造错误"实验至少亲手做过一遍；**或者**在同一处卡住超过 60 分钟 |
| `SOL-003` | **看过之后必须关掉参考解，从空文件重敲一遍**。只有这样才算满足该关的 `LvNN-A06`（"代码是自己敲的，不是复制的"） |
| `SOL-004` | `solutions/LvNN/` 一经写入即为**历史快照，不得随项目演进而修改**。工程后来怎么改都与它无关（与 `docs/` 的"只追加"同级） |
| `SOL-005` | 参考解的验收标准与关卡讲义 §9 **完全一致**，不另立标准 |
| `SOL-006` | 新增 `solutions/LvNN/` 必须同步：更新本文件索引 → 更新 `docs/README.md` 文档地图 → 在 `docs/12-变更记录.md` 登记 `CHG-*` → 打 git tag `lvNN-pass` |

⚠️ **违反 `SOL-004` 是最容易犯的错**：不要因为"工程后来改了"就回头去改 `solutions/Lv01/`。
如果某一关的参考解本身写错了，走 [`docs/00 §4.2`](../docs/00-文档使用与维护规范.md) 的勘误流程 —— 原文保留，另加勘误说明。
