## 1. 每关固定的 10 步交付格式

📎 原始出处：

> 每一关我会给你：
> ① 本关目标 → ② 为什么学 → ③ 环境准备 → ④ 手把手写代码 → ⑤ 让你自己敲 → ⑥ 故意制造错误 → ⑦ 解释原理 → ⑧ 小练习 → ⑨ 通关标准 → ⑩ 下一关。

### 1.1 编号与作用对照

| 步 | 编号 | 标题 | 作用 | 必须包含 |
| --- | --- | --- | --- | --- |
| ① | `LvNN-S1` | 本关目标 | 完成后能做到什么 | 3~5 条可验证的句子 |
| ② | `LvNN-S2` | 为什么学 | 没有它会出什么问题 | 一个具体的、会痛的场景 |
| ③ | `LvNN-S3` | 环境准备 | 本关需要安装/配置什么 | 版本、命令、验证方式 |
| ④ | `LvNN-S4` | 手把手写代码 | 完整可运行的最小示例 | 完整文件路径 + 可编译代码 |
| ⑤ | `LvNN-S5` | 你自己敲 | 关闭 §4 后独立复现 | 明确"不许看"的提示 |
| ⑥ | `LvNN-S6` | 故意制造错误 | 破坏 → 观察 → 恢复 | 实验编号 `LvNN-E0n`、预期报错、原因 |
| ⑦ | `LvNN-S7` | 解释原理 | 总结机制与结论 | 必须回答 [§4 五个问题](#4-每关必答的五个问题) |

## 2. 每关教学用的「5 步教学法」

📎 原始出处：

> 例如今天学：第 5 关：IOC
> 我不会直接给你讲一大堆概念。而是：
> ① 先制造问题：new StudentService() 为什么不好？
> ② 让你自己发现问题：Controller依赖Service，Service依赖Mapper，Mapper又依赖其他东西
> ③ 引入 Spring：@Service
> ④ 做实验：删掉@Service ↓ 启动 ↓ 报错 ↓ 恢复 ↓ 启动成功
> ⑤ 最后才总结：IOC = 对象创建和管理交给Spring；DI = Spring把对象注入给需要它的对象；Bean = Spring容器管理的对象
> 这样你学到的东西会非常牢。

### 2.1 五步与十步的对应关系

| 5 步教学法 | 落在 10 步交付格式的哪里 |
| --- | --- |
| ① 先制造问题 | `§2 为什么学` |
| ② 让你自己发现问题 | `§5 你自己敲`（先踩坑）+ `§6 故意制造错误` |
| ③ 引入 Spring（引入解决方案） | `§4 手把手写代码` |
| ④ 做实验 | `§6 故意制造错误` |
| ⑤ 最后才总结 | `§7 解释原理` |

### 2.2 硬性要求

⚠️ **`§7 解释原理` 里不允许出现"没有在 §4~§6 出现过的新名词"。**
如果必须引入新名词，回到 `§4` 补一个最小示例，或写进 `§8 小练习` 作为延伸。

📌 这是防止变成"知识目录"的关键约束。

## 5. 实验设计规范（`LvNN-E0n`）

一个合格的实验必须**满足以下全部条件**，否则它不是实验，只是演示：

| # | 要求 | 说明 |
| --- | --- | --- |
| 1 | 有**破坏动作** | 删注解、改配置、断服务、写除零 |
| 2 | 有**明确预期** | 事先写下"我预计会报 XX 错" |
| 3 | 有**真实报错** | 必须复制真实报错的关键行 |
| 4 | 有**根因分析** | 报错文本里的哪一句是关键？为什么？ |
| 5 | 有**恢复动作** | 改回原样并能正常启动 |
| 6 | 有**实际现象**记录 | 与预期不一致时，记录差异（差异本身就是知识点） |

### 参考文档中的经典实验（已分配编号）

| 实验 ID | 关卡 | 动作 | 目的 |
| --- | --- | --- | --- |
| `Lv02-E01` | Lv02 | 把 `@GetMapping("/hello")` 改成 `@GetMapping("/student")` | 亲眼看到 Java 方法是怎么变成 HTTP 接口的 |
| `Lv06-E01` | Lv06 | 删掉 `@Service` → 启动 → 看报错 → 加回 | 理解 Bean 到底是什么 |
| `Lv12-E01` | Lv12 | `@Transactional` 方法中 `int x = 10 / 0;` | 看数据库发生什么，理解回滚 |

📎 原始出处：

> 然后我们故意修改：@GetMapping("/hello") ↓ @GetMapping("/student") 让你亲眼看到：Java 方法是怎么变成 HTTP 接口的。

> 然后专门做一个实验：删掉 @Service ↓ 启动项目 ↓ 看看报什么错 → 再加回来。

> 然后故意：
> @Transactional public void transfer() { updateA(); int x = 10 / 0; updateB(); }
> 看看数据库发生什么。

| 要求 | 反例 | 正例 |
| --- | --- | --- |
| 可验证 | "理解了 IOC" | "能不看资料说出：删掉 `@Service` 会报 `NoSuchBeanDefinitionException`，因为……" |

| 包含"不看资料" | — | "不看 §4 独立复现" |

## 7. 文档写作风格要求

| # | 要求 | 说明 |
| --- | --- | --- |
| 1 | 先问题、后概念 | 禁止"XX 是一个用于……的注解"这种开头 |
| 2 | 用第二人称 | "你会看到"、"你亲手改一下" |
| 3 | 代码要能跑 | 不写伪代码（除非明确标注 `伪代码`） |
| 4 | 报错原文保留 | 不用"报了个错"代替真实报错文本 |
| 5 | 每一节都能对应到 `LvNN-S*` | 便于跳转与引用 |
| 6 | 不用"简单来说"掩盖机制 | 简单不了就老实讲清 |
