## 1. 最终架构图

参考文档给出的最终结构（**原文未删改**）：

```
浏览器 / Vue
      ↓
    HTTP
      ↓
  Controller
      ↓
   Service
      ↓
    Mapper
      ↓
    MySQL

Redis ← Service

JWT ← 登录认证
```

📎 原始出处：

> 最终结构大概：
> 浏览器 / Vue ↓ HTTP ↓ Controller ↓ Service ↓ Mapper ↓ MySQL
> Redis ← Service
> JWT ← 登录认证

### 1.1 架构图（规范化重绘）

```
                    ┌───────────────┐
                    │  浏览器 / Vue  │
                    └───────┬───────┘
                            │ HTTP (JSON)
                            ▼
                 ┌──────────────────────┐
                 │      Filter /        │
                 │     Interceptor      │  ← Lv14/Lv17 JWT 校验
                 └──────────┬───────────┘
                            ▼
                 ┌──────────────────────┐
                 │     Controller       │  ← Lv02 接收请求、参数绑定、Lv15 参数校验
                 └──────────┬───────────┘
                            ▼
                 ┌──────────────────────┐
                 │      Service         │  ← Lv04 业务逻辑、Lv12 事务边界
                 └───┬──────────────┬───┘
                     │              │
                     ▼              ▼
          ┌──────────────┐   ┌─────────────┐
          │    Mapper    │   │    Redis    │  ← Lv13 验证码 / 缓存
          └──────┬───────┘   └─────────────┘
                 │
                 ▼
          ┌──────────────┐
          │   MySQL      │  ← Lv08
          └──────────────┘

横切关注点（Lv18 AOP）：访问日志 / 耗时统计
统一出口（Lv10/Lv11）：Result<T> + GlobalExceptionHandler
```

📌 **横切与统一出口是这条链路的两个"外壳"，不属于任何一层**：请求先过拦截器、进入 Controller、再经 Service/Mapper，出口统一由 `Result<T>` 包装、由 `GlobalExceptionHandler` 兜底。

## 2. 分层职责

| 层 | 包（见 [07 §1](07-代码规范与工程规范.md)） | 只做 | 绝不做 | 引入关卡 |
| --- | --- | --- | --- | --- |
| Controller | `PKG-controller` | 接收 HTTP、参数绑定与校验、调用 Service、返回 `Result<T>` | 写业务逻辑、直接调 Mapper、拼 SQL | Lv02 |
| Service | `PKG-service` | 业务规则、编排多个 Mapper、事务边界、抛业务异常 | 感知 `HttpServletRequest`、返回 `Result` | Lv04 |
| Mapper | `PKG-mapper` | SQL 与结果映射 | 写业务判断、调用 Service | Lv07 |
| Entity | `PKG-entity` | 映射数据库表，与表结构一致 | 加业务方法、当接口出入参 | Lv08 |
| DTO / VO | `PKG-dto` / `PKG-vo` | DTO 收进入参、VO 输出展示 | 直接映射表 | Lv16 |
| 公共 | `PKG-common` | `Result`、异常、常量、枚举 | 依赖 Service | Lv10 |

📌 这条边界就是非功能需求 `NFR-006`，属 `GL-*` 级别的硬约定，不得因"方便"而跨越。

## 3. 一次请求的完整旅程

以 `GET /students/1` 为例（到 Lv14 之后）：

```
① 浏览器 / Vue
   └─ GET /students/1
      Header: Authorization: Bearer <jwt>

② Filter / Interceptor                       ← Lv17
   ├─ 取出 Authorization
   ├─ JWT 解析 → 用户ID
   ├─ 判断身份/权限
   ├─ 失败 → 直接返回 Result{code:401}      ← Lv10 + Lv11
   └─ 成功 → 放行，把用户ID 放入上下文

③ Controller                                 ← Lv02
   ├─ @GetMapping("/students/{id}")
   ├─ @PathVariable 绑定 id = 1             ← Lv03
   ├─ @Valid 校验（若为写接口）              ← Lv15
   └─ 调用 studentService.getById(1)

④ Service                                    ← Lv04
   ├─ 业务判断：是否存在、是否有权查看
   ├─ 不存在 → throw BusinessException("学生不存在")   ← Lv11
   └─ 调用 studentMapper.getById(1)

⑤ Mapper                                     ← Lv07
   └─ SELECT * FROM student WHERE id = #{id}

⑥ MySQL                                      ← Lv08
   └─ 返回一行

⑦ 回程
   ├─ Mapper 把 ResultSet 映射为 Student 实体
   ├─ Service 把 Entity 转成 StudentVO       ← Lv16
   ├─ Controller 包成 Result.success(vo)     ← Lv10
   └─ HTTP 200 + JSON

横切：AOP 记录「用户 10001 / 接口 /students/1 / GET / 耗时 32ms」  ← Lv18
```

📌 这张旅程图是本套文档的**引用锚点**。任何时候"这段代码属于哪一层"，回到这里对照。

## 4. 架构演进时间线

📌 **本表是"每学一个知识点，立刻看到它解决了什么问题"的架构侧落地。**
每通关一关，回来把该关的「架构变化」列填写完整（填充，不删除）。

| 关卡 | 新增/变化 | 架构上发生了什么 | 没有它时代码什么样 | 状态 |
| --- | --- | --- | --- | --- |
| Lv01 | Spring Boot 内嵌 Tomcat | 出现"能监听 8080 的进程" | 需自己装 Tomcat、打 war 包部署 | ✅ |
| Lv02 | `@RestController` + `@GetMapping` | 出现 **Controller 层** | 只有 Java `main`，无法被 HTTP 触达 | 🚧 |
| Lv03 | HTTP 方法语义 / `@PathVariable` / `@RequestParam` / `@RequestBody` | Controller 具备完整出入参能力，出现 **DTO 雏形** | 只能读死路径，无法区分查询与新增 | 🚧 |
| Lv04 | 抽 **Service 层** | 从 1 层变 2 层（Controller-Service） | Controller 里查库+判权+业务+返回，30 个接口必然失控 | 🚧 |
| Lv05 | IOC 容器管理对象 | 对象创建权从"代码"转移到"容器" | 到处 `new`，依赖写死 | 🚧 |
| Lv06 | DI / Bean / 构造器注入 | 层与层之间通过容器连接，出现 `@Service` `@Repository` 等术语 | `new StudentService()` 写死在 Controller 里 | 🚧 |
| Lv07 | 引入 MyBatis，抽 **Mapper 层** | 从 2 层变 3 层（Controller-Service-Mapper） | Service 里手写 JDBC | 🚧 |
| Lv08 | 真正连接 **MySQL** | 数据持久化落地，出现 **Entity** | 数据只在内存里 | 🚧 |
| Lv09 | CRUD 全部打通 | **学生管理系统 V1.0 成立**（接口与表齐备） | 只有一个接口能跑 | 🚧 |
| Lv10 | 统一返回 `Result<T>` | 出现 **统一出口**，Controller 返回值类型统一 | 有时返回对象、有时返回字符串 | 🚧 |
| Lv11 | `@RestControllerAdvice` | 出现 **全局异常出口**，Service 可以放心 `throw` | 堆栈直接返回浏览器 | 🚧 |
| Lv12 | `@Transactional` | Service 方法成为**事务边界** | A 扣钱成功、B 加钱失败 → 数据不一致 | 🚧 |
| Lv13 | 接入 **Redis** | 出现旁路存储，Service 同时依赖 Mapper 与 Redis | 验证码存内存，重启即丢、无法过期 | 🚧 |
| Lv14 | **JWT 认证** | 链路前面插入认证环节，接口开始"需要身份" | 任何人不带凭证就能查所有数据 | 🚧 |
| Lv15 | 参数校验 | Controller 入参处出现校验层，Service 不再重复判空 | 每个接口开头一堆 `if (x == null)` | 🚧 |
| Lv16 | DTO / VO | 层间传输对象与数据库实体解耦 | Entity 直接进出，改表即改接口 | 🚧 |
| Lv17 | `HandlerInterceptor` | 认证逻辑从 Controller 上移到**拦截器** | 每个方法开头写一遍 Token 校验 | 🚧 |
| Lv18 | AOP | 出现**横切层**，日志与业务解耦 | 日志代码散落每个方法 | 🚧 |
| Lv19 | 分页 | 查询链路加上 `page` / `pageSize` 与 `LIMIT/OFFSET` | 全表返回，数据量一大 OOM | 🚧 |
| Lv20 | 文件上传 | 出现**文件存储**外部依赖（磁盘/OSS），表中新增 URL 字段 | 图片塞 Base64 进 JSON | 🚧 |
| Lv21 | Spring Security | 认证授权体系化，替代/包裹自定义拦截器 | 权限判断散落在各处 | 🚧 |
| Lv22 | RabbitMQ | 出现**异步链路**，Service 只投递消息不等结果 | 同步调用导致接口变慢、失败即丢 | 🚧 |
| Lv23 | WebSocket | 出现**服务端主动推送**通道 | 前端只能轮询 | 🚧 |
| Lv24 | Docker | 出现**运行环境标准化**，应用与中间件容器化 | 换台机器就跑不起来 | 🚧 |
| Lv25 | Vue3 联调 | 前端成为独立消费者，**真正的前后端分离**成形 | 只能用 Postman 验证 | 🚧 |

### 5.6 Lv01 实测快照（2026-09-14）

> 📌 本节为 **Lv01 通关**时的真实架构，由实测得出，位于 §5.1（第一阶段结束）之前，属追加记录。

```
（此时还没有任何业务代码）

  java -cp <target/classes;35 个 jar> com.campus.CampusApplication
        │
        ▼
  SpringApplication.run()
        │
        ├── Environment   ← 读 application.yml（server.port=8080 / spring.application.name=campus）
        ├── ApplicationContext   ← 组件扫描 + 自动配置（此处只有 0 个自定义 Bean）
        └── 内嵌 Tomcat 10.1.55   ← 由 ServletWebServerFactoryAutoConfiguration 创建
                 │
                 ▼
        0.0.0.0:8080 LISTENING

  任何请求 → DispatcherServlet → 找不到映射 → Whitelabel Error Page (404)
```

**实测数据**

| 指标 | 值 |
| --- | --- |
| 自定义 Bean 数 | 0（只有框架自己的） |
| 容器初始化 | 615 ms |
| 启动总耗时 | 1.27 s |
| 依赖 jar 数 | 35 |
| 对外暴露的端点 | 只有 `/error`（Spring Boot 兜底），没有任何业务接口 |

**架构结论**：这一关没有新增"层"，新增的是**一个可运行的宿主环境**。
后续每一关做的事情，都是往这个已经跑起来的容器里添加东西。
📌 这也解释了为什么 Lv02 的第一个接口一写就能用 —— 通道早已铺好，只是没有映射。

## 6. 边界与硬约定

| # | 约定 | 违反后果 | 检查关卡 |
| --- | --- | --- | --- |
| 1 | Controller 只能调用 Service，不能调用 Mapper | 事务失效、逻辑重复、无法测试 | Lv04、Lv09 |
| 2 | Service 不能感知 HTTP 对象（`HttpServletRequest` / `Result`） | 业务层与传输层耦合，无法复用 | Lv04、Lv10 |
| 3 | Mapper 接口只放 SQL 映射，不放业务判断 | 业务散落，无法回归测试 | Lv07 |
| 4 | Entity 不得直接作为接口出入参 | 数据库结构泄漏，改表即改接口 | Lv16 |
| 5 | 异常必须在 Service 抛出、由全局处理器统一转换 | 堆栈外泄、前端无法处理 | Lv11 |
| 6 | `@Transactional` 只加在 Service 方法上 | 加在 Controller 或 private 方法上不生效 | Lv12 |
| 7 | 所有列表接口必须分页 | OOM | Lv19 |
| 8 | 所有出参统一 `Result<T>` | 前端无法统一处理 | Lv10 |
