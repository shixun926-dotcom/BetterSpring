## 2. 为什么学 `Lv25-S2`

先制造问题。到目前为止，"前端"一直是 Postman。

**但真实用户不会用 Postman。**

你启动了一个 Vue 工程：

```
前端：http://localhost:5173
后端：http://localhost:8080
```

在 Vue 里写：

```js
fetch('http://localhost:8080/students?page=1&pageSize=10')
```

**浏览器控制台报错：**

```
Access to fetch at 'http://localhost:8080/students' from origin 'http://localhost:5173'
has been blocked by CORS policy: No 'Access-Control-Allow-Origin' header is present.
```

**关键问题：Postman 能通，浏览器却不行。**

| # | 问题 | 原因 |
| --- | --- | --- |
| 1 | 为什么 Postman 能通 | Postman **不是浏览器**，不执行同源策略 |
| 2 | 谁在拦 | **浏览器**拦的，不是后端拦的 |
| 3 | 为什么要拦 | 防止恶意网站冒用你的身份去请求别的站点 |
| 4 | 端口不同算跨域吗 | **算**。协议、域名、端口任一不同即为跨源 |

📌 这个区别非常重要：

> **CORS 是浏览器的安全机制，不是后端的限制。**
> 后端要做的不是"解除限制"，而是"**明确告诉浏览器：这个来源我允许**"。

📌 参考文档把 Vue3 放在最后一关，位置很合理：
**到这一步，你才会真正理解前面每一层设计的意义** ——
为什么统一返回？为什么异常要统一？为什么 Token 要放 Header？为什么列表要分页？

这些在 Postman 里都"看不出好处"，**一接前端全部显形**。

## 4. 手把手写代码 `Lv25-S4`

### 4.1 跨域：两种方案

**方案一：后端开 CORS（推荐用于学习阶段）**

```java
@Configuration
public class CorsConfig implements WebMvcConfigurer {

    @Override
    public void addCorsMappings(CorsRegistry registry) {
        registry.addMapping("/**")
                .allowedOriginPatterns("http://localhost:5173")   // ⚠️ 不要写 "*" 配合 credentials
                .allowedMethods("GET", "POST", "PUT", "DELETE", "OPTIONS")
                .allowedHeaders("*")
                .allowCredentials(true)
                .maxAge(3600);
    }
}
```

**方案二：前端开发代理（推荐用于开发阶段）**

```js
// vite.config.js
export default defineConfig({
  server: {
    proxy: {
      '/api': {
        target: 'http://localhost:8080',
        changeOrigin: true,
        rewrite: path => path.replace(/^\/api/, '')
      }
    }
  }
})
```

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| 后端 CORS | 生产也能用；前端代码不用改 | 要维护来源白名单 |
| 前端代理 | 开发时**完全不跨域**（同源），不碰后端 | 只解决开发阶段；生产要另配（Nginx 代理） |

📌 两者**不冲突**，常见做法是：开发用代理，生产用 Nginx 同源部署或后端 CORS。**本项目建议两者都配，并在文档里写清各自的使用场景。**

⚠️ **预检请求（OPTIONS）**：带自定义头（如 `Authorization`）或非简单 `Content-Type` 的请求，浏览器会先发一个 `OPTIONS` 预检。
**如果 [Lv17](Lv17-拦截器.md)/[Lv21](Lv21-SpringSecurity.md) 把 OPTIONS 拦住了，所有跨域请求都会失败。** 这通常是一个很隐蔽的 bug。

### 4.2 统一的请求封装（前端最该写对的一处）

```js
// src/api/request.js
import axios from 'axios'

const request = axios.create({
  baseURL: '/api',
  timeout: 10000
})

// 请求拦截：自动带上 Token
request.interceptors.request.use(config => {
  const token = localStorage.getItem('token')
  if (token) config.headers.Authorization = `Bearer ${token}`
  return config
})

// 响应拦截：统一处理 Result<T>
request.interceptors.response.use(
  response => {
    const res = response.data          // ← { code, msg, data }
    if (res.code === 200) return res.data     // 只把 data 交给业务代码
    // 🚧 待补充：非 200 的业务错误怎么处理（提示：提示 msg）
    return Promise.reject(new Error(res.msg))
  },
  error => {
    // 🚧 待补充：401 → 跳登录；403 → 提示无权限；500 → 提示服务器错误
    return Promise.reject(error)
  }
)

export default request
```

📌 **这就是 [Lv10](Lv10-统一返回结果.md) 和 [Lv11](Lv11-异常处理.md) 的回报**：
如果没有统一结构，这段拦截器根本写不出来，每个接口都要单独判断返回长什么样。

### 4.3 登录链路

```js
// 登录
const token = await login({ username, password })
localStorage.setItem('token', token)

// 后续所有请求自动带上 Authorization 头（见 §4.2 的请求拦截器）
```

⚠️ **Token 存储位置的取舍**（本关必答）：

| 位置 | 优点 | 缺点 |
| --- | --- | --- |
| `localStorage` | 简单、刷新不丢 | 可被 XSS 读取 |
| `sessionStorage` | 关标签页即失效 | 同上 |
| `Cookie`（HttpOnly） | XSS 读不到 | 需后端配合；跨域设置复杂 |

📌 选定后在 [附录 A](#附录-a--追加区) 记录理由，并回填 [06 §5](../06-接口规范.md#5-认证约定)。

### 4.5 部署（与 [Lv24](Lv24-Docker.md) 结合）

```
前端 npm run build → dist/
        ↓
   由 Nginx 提供静态文件
        ↓
   /api/** 反向代理到后端容器
```

```nginx
server {
    listen 80;
    location / {
        root /usr/share/nginx/html;
        try_files $uri $uri/ /index.html;     # ← 前端路由刷新不 404
    }
    location /api/ {
        proxy_pass http://app:8080/;
    }
}
```

📌 这样部署后**前后端同源**，生产环境**根本不需要 CORS**。
📌 `try_files ... /index.html` 是 Vue Router history 模式必须配的，否则用户刷新页面会 404。
