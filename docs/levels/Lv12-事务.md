## 2. 为什么学 `Lv12-S2`

先制造问题。

```java
public void transfer(Integer fromId, Integer toId, BigDecimal amount) {
    accountMapper.decrease(fromId, amount);    // A -100
    accountMapper.increase(toId, amount);      // B +100
}
```

现在在两句中间插一行：

```java
accountMapper.decrease(fromId, amount);   // ✅ 执行成功，已提交
int x = 10 / 0;                           // 💥 抛异常
accountMapper.increase(toId, amount);     // ❌ 永远执行不到
```

**结果：A 的钱少了 100，B 的钱没变。100 块凭空消失。**

你的代码没有任何地方能阻止它 —— 因为两次 `update` 是两次独立的数据库操作，第一次提交后就不会回头。

| # | 问题 | 后果 |
| --- | --- | --- |
| 1 | 中途失败留下中间状态 | 数据不一致，且**无法自动恢复** |
| 2 | 没有"全做或全不做"的机制 | 业务规则只能靠人肉保证 |
| 3 | 异常被 `Lv11` 的处理器兜住了，接口返回 500 | 但**数据库已经脏了** |

📌 参考文档的态度很明确：

> 这比背："@Transactional 用于声明式事务管理。" 有用得多。

### 4.2 无事务版本（先写这个）

```java
@Service
public class TransferService {

    private final AccountMapper accountMapper;

    public TransferService(AccountMapper accountMapper) {
        this.accountMapper = accountMapper;
    }

    public void transfer(Integer fromId, Integer toId, BigDecimal amount) {
        accountMapper.decrease(fromId, amount);
        // int x = 10 / 0;                 // ← 实验时打开这一行
        accountMapper.increase(toId, amount);
    }
}
```

### 4.3 加事务

```java
@Service
public class TransferService {

    // ...

    @Transactional
    public void transfer(Integer fromId, Integer toId, BigDecimal amount) {
        accountMapper.decrease(fromId, amount);
        // int x = 10 / 0;
        accountMapper.increase(toId, amount);
    }
}
```

📎 参考（`Consult.txt` · 故意实验）：

> 然后故意：
> @Transactional
> public void transfer() {
>     updateA();
>     int x = 10 / 0;
>     updateB();
> }
> 看看数据库发生什么。

### 4.4 运行与验证（本关最重要的动作）

**必须做四次比对：**

| # | 版本 | 是否抛异常 | A 的余额 | B 的余额 | 结论 |
| --- | --- | --- | --- | --- | --- |
| 1 | 无 `@Transactional` | 否 | -100 | +100 | 正常 |
| 2 | 无 `@Transactional` | 是（`10/0`） | **-100** | **不变** | 💥 数据不一致 |
| 3 | 有 `@Transactional` | 否 | -100 | +100 | 正常 |
| 4 | 有 `@Transactional` | 是（`10/0`） | **不变** | **不变** | ✅ 已回滚 |

📌 第 2 行和第 4 行的对比，就是本关的全部价值。**必须亲手跑出来。**

🚧 待补充：实际执行记录（含每次执行前后的余额）。

### 4.5 关键补充：`@Transactional` 放在哪一层

```java
// ✅ 正确：Service 的 public 方法
@Service
public class TransferService {
    @Transactional
    public void transfer(...) { ... }
}

// ⛔ 错误：Controller（事务边界不该在传输层）
// ⛔ 错误：private 方法（代理不生效，静默失效）
// ⛔ 错误：Mapper（Mapper 不写业务）
```

📌 这就是 [04 §6 边界与硬约定](../04-系统架构与技术演进.md#6-边界与硬约定) 第 6 条的来源。

## 10. 下一关 `Lv12-S10`

事务解决了"要么全做，要么全不做"。但还有一类需求它管不了。

假设你要做登录验证码：

```
用户点击"获取验证码"
  ↓
服务端生成 928371
  ↓
存到哪里？
  ↓
5 分钟后自动失效
```

**存到 MySQL 里行不行？**
行，但你得：建一张表、每次写一条、再写个定时任务扫过期数据、还要考虑并发删。

而且验证码这种东西**读一次就没用了**，它天生不适合放在磁盘数据库里。
