## 2. 为什么学 `Lv19-S2`

先制造问题。

你的 `GET /students` 现在是这样：

```java
public List<Student> list() {
    return studentMapper.selectAll();     // SELECT * FROM student
}
```

**往表里插 10 万条数据，然后再调一次。**

会发生什么：

| # | 现象 | 原因 |
| --- | --- | --- |
| 1 | MySQL 要把 10 万行读出来 | 全表扫描 |
| 2 | MyBatis 要构造 10 万个 Java 对象 | 内存暴涨 |
| 3 | JSON 序列化 10 万个对象 | CPU 打满 |
| 4 | 网络传输几十 MB | 响应极慢 |
| 5 | 浏览器渲染 10 万行 | 页面卡死 |
| 6 | 严重时直接 OOM | 服务崩溃 |

**关键点：数据量小的时候完全看不出问题。** 这就是为什么它危险 —— 开发环境 3 条数据跑得好好的，上线一周后崩了。

分页解决的就是这件事：**只查你要看的那一页。**

📌 一个重要判断：**分页必须在 SQL 层做，不能在内存里做。**

| 方式 | SQL | 问题 |
| --- | --- | --- |
| ⛔ 内存分页 | `SELECT * FROM student` 然后 `list.subList(0, 10)` | 10 万行**已经全部读出来了**，内存与 IO 的开销一点没省 |
| ✅ SQL 分页 | `SELECT * FROM student LIMIT 10 OFFSET 0` | 数据库只返回 10 行 |

📌 参考文档把"分页"放在 Lv19，紧跟在 AOP 之后，位置很合理：
**它是第一个"为了性能和稳定性而改变写法"的关卡**，而不是"为了实现功能"。

## 4. 手把手写代码 `Lv19-S4`

### 4.1 请求参数与响应结构（以 [06 §4](../06-接口规范.md#4-分页返回结构) 为准）

**请求**

| 参数 | 类型 | 必填 | 默认 | 约束 |
| --- | --- | --- | --- | --- |
| `page` | `Integer` | 否 | `1` | ≥ 1 |
| `pageSize` | `Integer` | 否 | `10` | 1 ≤ pageSize ≤ 100 |

**响应**

```json
{
  "code": 200,
  "msg": "success",
  "data": {
    "total": 1000,
    "page": 1,
    "pageSize": 10,
    "list": [ { "id": 1, "name": "张三", ... } ]
  }
}
```

### 4.2 分页 VO

```java
package com.campus.vo;

@Data
public class PageVO<T> {
    private Long total;
    private Integer page;
    private Integer pageSize;
    private List<T> list;
    // 🚧 待补充：pages / hasNext 是否加入，见 06 附录 B B.3
}
```

### 4.3 SQL（核心）

```xml
<select id="selectPage" resultType="com.campus.entity.Student">
    SELECT *
    FROM student
    <where>
        <!-- 🚧 待补充：条件查询（FR-S-007）
             <if test="name != null and name != ''">
                 AND name LIKE CONCAT('%', #{name}, '%')
             </if>
        -->
    </where>
    ORDER BY id
    LIMIT #{pageSize} OFFSET #{offset}
</select>

<select id="countPage" resultType="long">
    SELECT COUNT(*)
    FROM student
    <!-- 🚧 待补充：与上面完全一致的条件 -->
</select>
```

📌 **`OFFSET` 的换算**：`offset = (page - 1) * pageSize`。
`page = 1, pageSize = 10` → `offset = 0`；`page = 2` → `offset = 10`。
**这个换算必须能自己推出来，不要靠背。**

📌 **条件必须"两条 SQL 完全一致"**：列表和总数用的 `WHERE` 一旦不一致，就会出现"总共有 100 条但翻到第 3 页是空的"这类诡异 bug。

### `Lv19-E03` · 内存分页

| 项 | 内容 |
| --- | --- |
| 破坏动作 | 先 `selectAll()` 再 `subList(0, 10)` |
| 预期现象 | 🚧 待补充（结果"看起来对"，但耗时呢？） |

### `Lv19-E04` · 条件不一致

| 项 | 内容 |
| --- | --- |
| 破坏动作 | 列表 SQL 带 `WHERE name LIKE ...`，总数 SQL 不带 |
| 预期现象 | 🚧 待补充（总数偏大 → 翻到后面几页是空的） |
| 实际现象 | 🚧 待补充 |
| 恢复动作 | 两条 SQL 条件保持一致 |
| 状态 | ⬜ |

### `Lv19-E05` · 没写 `ORDER BY` 就分页

| 项 | 内容 |
| --- | --- |
| 破坏动作 | `LIMIT/OFFSET` 但去掉 `ORDER BY` |
| 预期现象 | 🚧 待补充（提示：多次请求结果顺序可能不同 → 翻页时出现重复或遗漏） |
| 实际现象 | 🚧 待补充 |
| 恢复动作 | 加稳定的 `ORDER BY id` |
| 状态 | ⬜ |

### `Lv19-E06` · 深分页性能

| 项 | 内容 |
| --- | --- |
| 破坏动作 | 请求一个很大的页码（如 `page=9000&pageSize=10`） |
| 预期现象 | 🚧 待补充 |
| 实际现象 | 🚧 待补充（提示：`OFFSET` 很大时数据库仍需扫描前面所有行） |
| 优化方向 | 游标分页（`WHERE id > lastId`） |
| 状态 | ⬜ |

### `Lv19-E07` · 用 `${}` 拼 `LIMIT`

| 项 | 内容 |
| --- | --- |
