## 2. 为什么学 `Lv22-S2`

先制造问题。

**需求**：学生选课成功后，给学生发一条通知。

**第一版：直接调用**

```java
@Transactional
public void selectCourse(Integer studentId, Integer courseId) {
    courseSelectionMapper.insert(...);
    courseMapper.incrementSelected(...);
    noticeService.send(studentId, "选课成功");    // ← 同步调用
}
```

**问题清单：**

| # | 问题 | 后果 |
| --- | --- | --- |
| 1 | 发通知耗时 2 秒 | **选课接口要等 2 秒**（学生点了按钮转圈 2 秒） |
| 2 | 通知服务不可用 | **整个事务回滚 → 课没选上**。明明选课本身成功了 |
| 3 | 想加第二个动作（发邮件） | 改选课代码 |
| 4 | 通知服务要限流 | 改选课代码 |
| 5 | 高峰期通知服务被压垮 | 选课功能跟着一起挂 |

📌 第 2 条最致命：**"发通知失败"和"选课失败"是两件完全不同的事，但你的事务把它们绑在了一起。**

**正确做法**：选课成功后，只做一件事 —— **把"要发通知"这件事记下来，然后立刻返回。**

至于"谁来发、什么时候发、发失败怎么办"，交给另一个进程去操心。

这就是**消息队列**。

📌 一句话理解：

> **MQ = 一个可靠的"待办事项"中转站。**
> 生产者只管把事项放进去，消费者只管从里面取出来做。两边互不认识。

### 4.2 队列与交换机声明

```java
@Configuration
public class RabbitConfig {

    public static final String EXCHANGE = "campus.exchange";
    public static final String QUEUE_NOTICE = "campus.notice.queue";
    public static final String ROUTING_NOTICE = "notice.send";

    // 🚧 待补充：
    // @Bean Queue / DirectExchange / Binding
    // 注意：队列要设置 durable(true)（持久化）
}
```

📌 **三种交换机类型**（本关必须能区分）：

| 类型 | 路由方式 | 适用 |
| --- | --- | --- |
| `direct` | 按 routing key 精确匹配 | ✅ 本项目用这个 |
| `topic` | 按通配符匹配（`notice.*`） | 一类消息多种订阅 |
| `fanout` | 广播给所有绑定队列 | 事件通知 |

### 4.3 生产者（选课 Service 里）

```java
@Transactional
public void selectCourse(Integer studentId, Integer courseId) {
    // 1. 选课（核心业务，事务内）
    courseSelectionMapper.insert(...);
    courseMapper.incrementSelected(...);

    // 2. 投递消息（不是"发通知"，是"记下要发通知"）
    rabbitTemplate.convertAndSend(
            RabbitConfig.EXCHANGE,
            RabbitConfig.ROUTING_NOTICE,
            new NoticeMessage(studentId, "选课成功"));
}
```

📌 **关键理解**：这里做的事是"**记下要发通知**"，不是"发通知"。
所以它很快（毫秒级），而且不依赖通知服务是否活着。

⚠️ **重要陷阱**：消息投递**在事务内**，但消息**不受事务控制**。
如果消息已经投出去、事务随后回滚了 → **消费者会收到一条"不该发"的通知**。
这是经典的"本地事务与消息不一致"问题。本关只需**知道它存在**，解决方案（本地消息表 / 事务消息）留作 [附录 A 追加](../README.md#附录-a--追加区)。

### 4.5 运行与验证

```
① 调用选课接口 → **立刻返回**（不等待通知）
② RabbitMQ 管理台 → Queues → 看到消息进出
③ 控制台 → 消费者打印出通知内容
④ 停掉消费者（注释掉监听或停服务）→ 再选课
   → 接口**依然立刻成功**
   → 消息**堆积在队列里**
⑤ 恢复消费者 → 堆积的消息被消费掉
```

📌 第 ④、⑤ 步是本关最有力的证据：**消费者挂了，主流程不受影响。**

🚧 待补充：实际观察记录（含管理台截图或数字）。

### 4.6 幂等（必须设计）

**为什么消息会重复？** 至少三种情况：

| 情况 | 说明 |
| --- | --- |
| 消费者处理成功但 ack 丢失 | 队列以为没消费，重投 |
| 消费者处理中宕机 | 消息回队，重新投递 |
| 生产者重试 | 网络抖动导致重复发送 |

**所以消费者必须幂等**。常见做法：

```java
// 🚧 待补充：用 Redis 的 SETNX 做幂等键
// if (!redis.setIfAbsent("notice:sent:" + msgId, "1", Duration.ofHours(1))) return;
```

📌 参考 [Lv13](Lv13-Redis.md)：这里正好复用你学过的 Redis。这就是为什么 Redis 和 MQ 经常一起出现。

### 4.7 消息丢失的三个环节（本关必答）

| 环节 | 丢失可能 | 对策 |
| --- | --- | --- |
| 生产者 → Broker | 网络失败、Broker 挂了 | 发送确认（publisher confirm） |
| Broker 内部 | 未持久化 + 重启 | 队列 `durable` + 消息 `persistent` |
| Broker → 消费者 | 消费者未处理完就宕机 | 手动 ack + 处理成功后才 ack |

## 10. 下一关 `Lv22-S10`

MQ 解决了"服务端之间怎么异步"。

现在换一个方向：**服务端怎么主动告诉浏览器？**

场景：教师在后台录入了某个学生的成绩。此时这个学生正在页面上看自己的成绩列表。

- 学生不会知道数据变了，除非他自己刷新页面；
- 如果让他每 3 秒自动刷新一次（轮询），1000 个在线学生就是每秒 333 次请求，**其中 99% 是白问的**。

**问题**：HTTP 是"客户端问、服务端答"。服务端没法主动开口。

下一关：**WebSocket**。
