# 00 · 文档使用与维护规范

> 本文档是整个文档集的**宪法**。
> 任何一次编辑之前，先读本文档；任何一次编辑之后，在本文件 [§8](#8-变更登记要求) 约定的位置登记。
>
> **一句话总纲：可以完善，不可以随意删改。**

---

## 1. 为什么需要这份规范

参考文档 `Consult.txt` 已经给出了完整的 9 阶段 25 关路线，但它是一份**对话记录**：

- 没有编号，引用困难（"第 5 关那个实验" 指代不清）；
- 结构不固定，每关详略不一；
- 一旦开始学习，会不断产生新内容（踩坑、补充实验、验收结论、勘误）。

如果直接在上面改，会出现三个必然问题：

1. **改一处、坏一片** —— 前面的验收标准被后面新理解推翻，旧记录丢失；
2. **无法判断"这关到底过没过"** —— 结论被覆盖，只剩最新说法；
3. **回不去** —— 想复习"我当初为什么这么写"时，原始内容已经不在。

所以本文档集采用 **稳定编号 + 只追加 + 显式废弃** 三条规则。

## 2. 编号规范

### 2.1 文件命名

| 类型 | 位置 | 命名格式 | 示例 |
| --- | --- | --- | --- |
| 主文档 | `docs/` | `NN-名称.md`（NN 为 2 位数字） | `05-数据库设计.md` |
| 关卡文档 | `docs/levels/` | `LvNN-名称.md`（NN 为 2 位数字） | `Lv07-引入MyBatis.md` |
| 脚本 / 资源 | `docs/assets/`（预留） | 见 §2.4 | — |

📌 **编号一经分配永不回收、永不复用。**
即使某份文档作废，也**不删除文件、不释放编号**，而是把标题改为：

```markdown
# 07（已废弃 · 2026-XX-XX）· 代码规范与工程规范
> ⛔ 本文档已被 [13-XX](13-XX.md) 取代。
> 废弃原因：……
> 原文保留于文末「附录 Z · 废弃存档」。
```

### 2.2 章节编号

- 一级章节用 `## N. 标题`，N 从 1 开始连续。
- 二级用 `## N.M 标题`；更深的层级用 `###` / `####` 但不进入编号空间。
- **新章节一律追加在最后一个正文章节之后、`附录` 之前**，编号顺延。
- 不许"插入编号"（如给 3 和 4 之间加 `3.5`）。要插入内容时，追加为新编号并在此处留一行指向：

```markdown
## 3. 分层职责
（…原文不动…）
> 📎 补充内容见 [§9 分层职责补充（2026-XX-XX）](#9-分层职责补充2026-xx-xx)。
```

### 2.4 锚点规则

中文标题在 Markdown 中会生成不可靠的锚点。**跨文档链接必须写作 `<文档路径>#<可见标题文本>`**，且标题文本中不得包含会变化的编号。

- ✅ `[通关标准](levels/Lv07-引入MyBatis.md#9-通关标准-lv07-s9)`
- ⛔ 不要使用页内纯 `#` 链接跨文件引用。
- 📌 **锚点规则补充（2026-09-14，CHG-004 自检发现）**：`——`（中文破折号）会被 GitHub 从锚点中**整体删除**，
  不像空格那样变成连字符；而每一个空格都各自变成一个连字符，**连续空格会产生连续连字符**。
  例：标题 `### 5.3 第三阶段结束时（Lv09 后）—— 学生管理系统 V1.0`
  → 锚点 `#53-第三阶段结束时lv09-后-学生管理系统-v10`（`——` 与括号消失，`后` 与 `学生` 之间只有一个连字符）。

## 3. 增补规则（「可以完善」的定义）

### 3.1 允许的追加动作

| 动作 | 具体做法 |
| --- | --- |
| 补充内容 | 在对应章节下追加 `###` 子节，或追加到该文档的「附录 A · 追加区」 |
| 新增关卡 | 在 `docs/levels/` 新建 `LvNN-…md`，同步登记到 [08-关卡总览](08-关卡总览与路线图.md) 与 [README 关卡表](README.md) |
| 新增实验 | 追加到该关 §6，编号顺延 `LvNN-E0n` |
| 新增验收项 | 追加到该关 §9，编号顺延 `LvNN-A0n`。**旧验收项不得删除或修改** |
| 新增需求 / 接口 / 字段 | 追加到对应表格末尾，ID 顺延 |
| 追加笔记 | 该关「附录 A · 追加区」 |
| 追加踩坑 | 该关「附录 B · 踩坑记录」，编号 `LvNN-P0n` |
| 追加勘误 | 该文档「附录 C · 勘误」，并登记 `CHG-*` |

### 3.2 追加区的强制使用场景

以下内容**必须**写进追加区，不得插进正文中间：

1. 与已有结论**并列的新观点**（不是纠正）；
2. **超出本关原始范围**的延伸知识；
3. 未经实践验证的猜想、待验证笔记；
4. 个人化笔记（自己的理解、类比、口诀）。

### 3.3 追加的书写格式

```markdown
### A.3 xxx 补充（2026-09-20）

- 触发原因：……
- 内容：……
- 影响的关卡/文档：`Lv12`、[06-接口规范](06-接口规范.md)
- 是否改变了原有结论：否 / 是（若是，必须同时登记 CHG-* 并走 §4 流程）
```

📌 **每一条追加都必须带日期**，否则视为无效追加。

## 4. 禁改规则（「不可以随意删改」的定义）

### 4.1 禁止的动作

| ⛔ 禁止 | 原因 |
| --- | --- |
| 删除已有章节 / 表格行 / 段落 | 丢失可追溯性 |
| 修改已通关关卡的 §1 目标、§9 通关标准 | 验收标准一改，历史验收结论全部失效 |
| 修改已登记的 `FR-*` / `API-*` / `EC-*` 的含义 | 破坏 ID 的跨文档引用 |
| 修改已存在的 `T-*` 字段名或类型 | 破坏数据库迁移记录与代码引用 |
| 静默修改任何结论（不加日期、不登记 `CHG-*`） | 无法判断哪个是最新结论 |
| 删除「待决事项」「待补充」占位 | 丢失"还欠什么"的清单 |
| 删除他人（或过去的自己）写的追加区条目 | 同第一条 |

### 4.2 确需改变已有内容时的四步流程

**原则：旧内容保留并显式标记，新内容另起编号追加。**

```
① 标注   在原文上方插入一行标注块（原文一个字都不动）
② 追加   在文档「附录 A 或 C」新增一条带日期的补充/勘误，写明"取代哪一条"
③ 登记   在 12-变更记录.md 新增一行 CHG-NNN
④ 同步   若影响其他文档或 ID 空间，同步追加（仍不删除）
```

**① 标注块的标准写法：**

```markdown
> ⚠️ **已被取代（2026-09-20）**：本条结论在 [CHG-014](12-变更记录.md) 中被修正，
> 请以 [附录 C.1 勘误](#c1-勘误2026-09-20) 为准。以下原文保留，不得修改。
```

**② 勘误条目标准写法：**

```markdown
### C.1 勘误（2026-09-20）

- **CHG**：CHG-014
- **被修正对象**：§3 分层职责 · 第 2 段
- **原结论**：Controller 可以直接调用 Mapper。
- **修正后结论**：Controller 只依赖 Service；跨层调用属违规，见 [07-代码规范 §3](07-代码规范与工程规范.md)。
- **修正原因**：Lv09 实践后发现跨层导致事务失效。
- **原文处置**：保留于原位，已加「已被取代」标注。
```

### 4.3 升级为"版本级"变更

若修正会同时影响**三个以上文档**或**某个已通关关卡的验收标准**，则不走单条勘误，而在 [12-变更记录](12-变更记录.md) 记为一个**阶段版本**（`v0.1.0 → v0.2.0`），并在受影响文档顶部加：

```markdown
> **本文档在 v0.2.0 中被部分取代**，差异清单见 [12-变更记录 §版本 v0.2.0](12-变更记录.md)。
```

## 5. 占位符规范

骨架阶段每关大量使用占位符。占位符是**任务清单**，不是"可以忽略的装饰"。

### 5.1 三种占位符

| 写法 | 含义 | 何时消失 |
| --- | --- | --- |
| `🚧 待补充` | 需要人来写的内容（讲解、代码、图） | 内容写好即替换；但**必须在原位置留下替换记录**（追加到附录 A） |
| `🚧 待定（见 README 附录 B.Bn）` | 需要做决定才能写的内容 | 决定后在 README 附录 B 对应行右侧补「结论」，再回来填写 |
| `<!-- TODO(Lv07-S4): 补 XML 版示例 -->` | 写在注释里的细粒度待办 | 完成后删除该注释（这是**唯一**允许直接删除的行，因为它是脚手架不是内容） |

### 5.2 占位符的统计

[10-学习进度记录](10-学习进度记录.md) 中的「待补充项数」列用于统计。建议每完成一次学习就更新一次，避免骨架永远只是骨架。

## 6. 状态标记

| 标记 | 名称 | 判定标准 |
| --- | --- | --- |
| ⬜ | 未开始 | 只有骨架，无实质内容 |
| 🟡 | 进行中 | 已开始动手，尚未通过验收 |
| 🔁 | 返工中 | 验收未通过，正在修正 |
| ✅ | 已通关 | 该关 §9 全部验收项 `LvNN-A*` 均判定通过 |
| ⏸ | 暂停 | 主动搁置（需在进度记录写明原因） |
| ⛔ | 阻塞 | 外部依赖缺失，无法推进（需写明缺什么） |

📌 **状态只能「⬜ → 🟡 → (🔁) → ✅」推进**，不得回退为 ⬜。若发现关卡需要重做，标记为 🔁 并追加说明。

## 7. 每个知识点必须回答的问题

这是参考文档的核心方法论，作为对**所有新增内容**的强制要求：

> 每学一个知识点，都能立刻看到它解决了什么问题。

任何新增章节，若涉及一个知识点，必须至少覆盖：

```
① 没有它的时候，会发生什么问题？   （问题先行）
② 它怎么解决的？                  （机制）
③ 亲自做实验验证（能失败的实验）    （🧪 实验）
④ 一句话总结它是什么               （结论）
⑤ 它出现了，哪一层变了？            （回到架构，见 04-架构演进）
```

不满足这五点的内容，写进该文档的「附录 A · 追加区」，**不得并入正文**。

## 10. 参考解使用规则

📌 每一关的通关参考解放在 [`solutions/LvNN/`](../solutions/)，**它是答案，不是教材**。
完整说明见 [`solutions/README.md`](../solutions/README.md)。

| ID | 规则 |
| --- | --- |
| `SOL-001` | 参考解只用于**对照和卡住时的解救**，不得作为默认阅读顺序。学习时只打开当前关卡讲义 |
| `SOL-002` | **允许查看的门槛**：本关 §6 的"故意制造错误"实验至少亲手做过一遍；**或者**在同一处卡住超过 60 分钟 |
| `SOL-003` | **看过之后必须关掉参考解，从空文件重敲一遍**。只有这样才算满足该关 `LvNN-A06`（"代码是自己敲的，不是复制的"） |
| `SOL-004` | `solutions/LvNN/` 一经写入即为**历史快照，不得随项目演进而修改**。工程后来怎么改都与它无关 |
| `SOL-005` | 参考解的验收标准与关卡讲义 §9 **完全一致**，不另立标准 |
| `SOL-006` | 新增 `solutions/LvNN/` 必须同步：`solutions/README.md` 索引 → 本文件 §2.3 编号空间 → [README 文档地图](README.md) → [12-变更记录](12-变更记录.md) 登记 `CHG-*` → 打 git tag `lvNN-pass` |

### 10.1 为什么要有参考解

`campus/` 展示的是**最终态**，不是**逐关态**。做到 Lv05 时，`campus/` 里已经混进了 Lv04、Lv05 的代码，
想回头看"Lv03 那关当时代码该长什么样"已经做不到。
`solutions/` 把每一关通关那一刻的工程状态冻结下来，补的就是这个缺口。

### 10.2 为什么必须限制它

本套文档最值钱的部分不是"代码长什么样"，而是**学习者自己把代码弄坏、看到报错、再修回来的过程**
（也就是每关 §6「故意制造错误」）。参考解一旦被当作默认阅读材料，这个过程就消失了，
`LvNN-A06`（"代码是自己敲的，不是复制的"）也随之落空 —— 那一关就白学了。

⚠️ **`SOL-004` 是最容易违反的一条**：不要因为工程后来改了，就回头去改 `solutions/Lv01/`。
若某一关的参考解本身写错了，走 [§4.2 勘误流程](#42-确需改变已有内容时的四步流程) ——
原文保留，另加勘误说明，并登记 `CHG-*`。

### 10.3 与 `campus/` 的分工

| 目录 | 是什么 | 可否修改 | 用于 |
| --- | --- | --- | --- |
| `campus/` | **活的工程**，随关卡不断演进 | ✅ 正常开发 | 开发、运行 |
| `solutions/LvNN/campus/` | **冻结的快照**，路径与 `campus/` 一一对应 | ⛔ 一经写入即冻结 | 对照、复习、卡住时解救 |

📌 想看某一关的**完整可运行状态**，用 git tag（避免 25 份工程副本）：

```bash
git checkout lv01-pass      # Lv01 通关那一刻的完整工程
git checkout main           # 回到最新
```
